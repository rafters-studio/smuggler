# westwind

The sample database every example in this directory uses. Eight tables in the shape most SQL readers already know: customers, orders, order details, products, categories, suppliers, employees, shippers. Forty customers, three hundred and twenty orders, seven hundred and eighty-eight order lines. Its schema is eight `smugglr migrate` manifests, applied by `smugglr migrate apply`, so a freshly built copy already carries a ledger with eight rows in it.

## Build it

`smugglr` on your PATH (or `SMUGGLR=/path/to/smugglr`) and the `sqlite3` shell.

```sh
./make.sh
```

`make.sh` creates an empty file, applies `migrations/01_create_categories.json` through `08_create_order_details.json` in order, loads `seed.sql`, and prints three counts. `./make.sh --empty ./target.db` applies the schema and skips the seed, which is what a sync target needs. A relative output path is taken from your directory, so `../westwind/make.sh ./local.db` from an example builds it there. The `.db` file is ignored by git; the manifests and `seed.sql` are the source.

## Why it looks the way it does

Every table's primary key is a UUIDv7 text column, declared `id:pk:notnull` in the manifest. smugglr's identity is the primary key, and a locally sequential integer key is the one shape it refuses: two machines both mint `id = 5` for different rows and one row silently wins. The short codes a report wants (`customers.code = 'WINTF'`) are plain columns beside the key.

Every table has `updated_at` in unix seconds. `newer_wins` orders on it, and the LAN mesh's `ordering_columns` default to it.

No column declares a foreign key. The relationships are real (`orders.customer_id` is a customer's `id`), and sync itself no longer needs the omission -- it writes tables in dependency order now, so a target that enforces foreign keys gets `orders` before `order_details` (#435). What still stops the scaffold from declaring them is narrower: `smugglr migrate new`'s `fk` modifier infers its target table by stripping a column's `_id` suffix, with no pluralization and no override, so `customer_id:fk` infers `customer`, not `customers` -- every reference here would name a table that does not exist. The sample stays syncable to every target it is used against by leaving enforcement to the application until the generator can name a plural target.

Two things the 0.5.0 scaffold cannot say, so the sample does without them: a composite unique constraint (Northwind's `(order_id, product_id)`), and a self-reference on `employees.reports_to`, since `fk` infers its table from a `<table>_id` name.

`seed.sql` is generated by `generate.py` from a fixed seed, so the ids, the dates, and the row counts are identical on every machine. Output captured against Westwind in one example's README is the output you get.

## Regenerate

```sh
./scaffold.sh              # rewrites migrations/ from the specs in the script
python3 generate.py        # rewrites seed.sql from the fixed seed
./make.sh
```

Change a spec in `scaffold.sh` and its manifest's checksum changes; change nothing and both files are byte-identical to the committed ones.
